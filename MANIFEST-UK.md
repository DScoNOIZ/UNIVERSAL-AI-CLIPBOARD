## 🌍 ПРОБЛЕМА

### Фундаментальна суперечність

Сучасні ШІ-агенти марнують **до 90% вихідного трафіку** на монотонну повторну генерацію вмісту, який уже є в контексті сесії.

Щоразу, коли модель пише команду, код-блок або текстовий фрагмент, вона генерує його заново з нуля, навіть якщо такий самий вміст було створено хвилину тому. Модель не має інструментального способу послатися на вже наявний вміст.

### Глобальний масштаб проблеми

- Мільйони ШІ-агентів працюють щодня по всьому світу
- Кожен із них виконує десятки викликів інструментів за сесію
- Значну частину кожного виклику становить повторна генерація наявного вмісту
- Це призводить до величезного споживання енергії, обчислювальних втрат і фінансових витрат

### Чому наявні підходи не розв'язують це

| Підхід                | Обмеження                                                       |
| ----------------------- | --------------------------------------------------------------- |
| **Кешування промптів**      | Працює лише зі статичними частинами, не з динамічним вмістом |
| **Семантичне кешування**    | Кешує за змістом запиту, не дозволяє цитувати фрагменти |
| **Стиснення контексту** | Стискає історію, але не дає інструменту цитування |
| **RAG**                 | Витягає із зовнішніх джерел, не використовує повторно внутрішній контекст |
| **Ланцюжки інструментів**       | Поєднує виклики в ланцюжок, не дозволяє посилатися на їхні результати  |

## 💡 РІШЕННЯ: UNIVERSAL AI CLIPBOARD

### Основна ідея

ШІ-агент отримує змогу **посилатися на вже наявний контекстний вміст** замість того, щоб заново його генерувати. Викликаючи будь-який інструмент, що приймає текстові параметри (команди, код, текст), агент може вказати: «візьми цей фрагмент звідти» — замість того, щоб писати його з нуля.

### Мозаїчна збірка: компонування інформації як пазла

На додачу до простого цитування «один до одного» ця концепція відкриває принципово новий спосіб компонування інформації — **мозаїчну збірку**.

Агент може **поєднати кілька фрагментів із різних джерел** в одній операції:

- Код з одного файлу
- Конфігурацію з історії чату
- Вивід команди з терміналу
- Результати із зовнішніх API

Агент може **редагувати на льоту** — змінювати, обгортати, замінювати текст усередині кожного фрагмента. Він може **перепорядковувати** фрагменти, **вкладати** одне в одне, **зливати** частини, що перетинаються, і **рекурсивно реструктурувати** вміст. Це дає змогу складати складені тексти, документи або код-блоки з розрізнених шматків — як майстер мозаїки, що викладає кольорові камінці у цілісну картину.

**Ключова думка:** замість того, щоб генерувати новий текст, модель діє як **редактор і куратор** наявного вмісту — значно ефективніше, точніше й менш схильна до помилок.

### Менеджер буфера обміну: іменовані слоти для тривалого збереження

Розширенням цієї концепції є **менеджер буфера обміну з іменованими слотами** — подібно до кількох буферів обміну або менеджера текстових буферів.

Агент може:

- **Зберігати фрагменти** в іменованих слотах (`clip-1`, `clip-2`, `config-block`, `error-log`, тощо)
- **Посилатися на слоти** за назвою, а не за вмістом — нуль токенів на опис
- **Обмінювати та реорганізовувати** вміст між слотами
- **Будувати складені документи**, послідовно посилаючись на кілька слотів
- **Зберігати фрагменти між сесіями** — збережені фрагменти переживають ущільнення контексту та перезапуски сесії

Це перетворює робочий процес ШІ-агента на аналог людини-розробника, що працює з кількома менеджерами буфера обміну, текстовими буферами та чернетками — але цілком автоматизовано й з нульовою вартістю токенів за операції збереження.

### Осьова відмінність від наявних механізмів

Усі наявні механізми цитування в ШІ (Citations API, Grounding, ContextCite) працюють на осі **«агент → користувач»** — вони показують людям, звідки агент узяв інформацію.

Universal AI Clipboard працює на осі **«агент → агент»** — він дозволяє самому агенту повторно використовувати вміст між власними викликами інструментів. Це принципово нова категорія.

| Механізм                  | Вісь              | Призначення                           |
| -------------------------- | ----------------- | --------------------------------- |
| Anthropic Citations        | Агент → Користувач      | Показати джерело відповіді             |
| OpenAI Citations           | Агент → Користувач      | Показати джерела                   |
| Google Grounding           | Агент → Користувач      | Підтвердження вебпошуку           |
| **★ UAC (це відкриття)** | **Агент → Агент** | **Повторне використання вмісту між викликами** |

## 🧩 П'ЯТЬ ОСНОВНИХ МЕХАНІЗМІВ

### Механізм 1: 🔗 Синтаксичний буфер обміну

Модель вказує лише один **якірний елемент** — ім'я функції, ім'я класу або змінну. Система автоматично:

1. Локалізує цей елемент у вказаному джерелі (файл, повідомлення чату, вивід команди)
2. Визначає його точні межі як синтаксичної одиниці
3. Витягує всю одиницю

**Економія:** кілька токенів за посилання замість тисяч токенів коду.

```
{ source: "file", path: "utils.ts", focus: "calculateSum" }
  → 2 токени замість 800+ токенів усієї функції
```

---

### Механізм 2: 📇 Цитування за парою якорів

Модель вказує лише **ПОЧАТОК** та **КІНЕЦЬ** бажаного фрагмента (по 15-40 символів). Система знаходить усе, що між ними, за допомогою багатоступеневого пошуку:

1. **Точний збіг** — фрагмент знайдено буквально (~70% випадків)
2. **Нормалізований збіг** — розбіжності в пробілах, регістрі та пунктуації ігноруються
3. **Нечіткий збіг** — дрібні описки допускаються (~9% випадків)
4. **Розширення до меж слів** — цілісність фрагмента

**Економія:** ~10 токенів за цитування замість 200+.

```
{ source: "chat", ref: "-1",
  start: "function calculateSum(",
  end: "return result;" }
  → ~10 токенів замість 200+
```

---

### Механізм 3: 🧠 Карта індексу повідомлень

Під час роботи з історією чату створюється окремий індекс — карта точних позицій символів для кожного повідомлення та кожного рядка в ньому. Модель пише коротке посилання на кшталт `"record_number:start_line..end_line"`, і система витягує точний фрагмент за позиціями символів.

**Ключова перевага:** модель ніколи не бачить сам індекс — лише коротке посилання (~5 токенів), але досягає 100% точності витягу.

```
{ source: "chat", ref: "167:14..18" }
  → "запис #167, рядки 14-18" → точне витягування за позиціями символів
```

---

### Механізм 4: 🔄 Конвеєр перетворень

Скопійований фрагмент можна **змінювати на льоту** — ще до того, як він потрапить до інструмента. Доступні операції:

- **Замінити** — змінити підрядок усередині фрагмента
- **Додати перед** — вставити текст перед фрагментом
- **Обгорнути** — помістити фрагмент у шаблон
- **Додати після** — дописати текст після фрагмента
- **З'єднати** (для кількох посилань) — об'єднати фрагменти роздільником

Усі операції застосовуються в одному виклику інструмента.

```
{ ref: { ... }, transform: { wrap: "try { {content} } catch (err) { }" } }
  → взяти функцію, обгорнути в try-catch і записати — все за 1 виклик
```

---

### Механізм 5: 🔁 Міжпротокольне цитування (MCP)

Маркери посилань можна вбудовувати безпосередньо в текстові параметри будь-яких інструментів, включно із зовнішніми MCP-серверами. Система автоматично розпізнає ці маркери і підставляє справжній вміст перед викликом зовнішнього сервера.

**Результат:** усі компоненти екосистеми обмінюються даними через єдиний механізм посилань, без потреби змінювати щось у схемах зовнішніх серверів.

```
"{{ref:source=chat,ref=-1,start=export const config}} --host example.com"
  → 91% вмісту з контексту, 9% згенеровано моделлю
```

## 📖 ПРИКЛАДИ ВИКОРИСТАННЯ

### Приклад 1: Повторне виконання команди з додатковими параметрами

Агент виконав тестову команду; у виводі з'явилася помилка. Щоб перезапустити з прапорцями налагодження, агент не переписує команду — він посилається на неї і додає прапорці:

```
{ ref: { source: "terminal", id: "cmd-xxx", start: "npx vitest" },
  transform: { append: " --verbose --timeout=30000" } }
  → результат: "npx vitest run --verbose --timeout=30000"
```

### Приклад 2: Складання кількох функцій в один файл

Агент читає файл із кількома функціями, після чого створює новий файл, збираючи потрібні функції через посилання:

```
{ multi_ref: [
    { source: "file", path: "handlers.ts", start: "async function validate(", end: "}" },
    { source: "file", path: "handlers.ts", start: "async function process(", end: "}" },
    { source: "file", path: "handlers.ts", start: "async function respond(", end: "}" }
  ],
  transform: { join: "\n\n", prepend: "// --- Handlers ---\n" } }
  → три функції об'єднано в один файл за 1 виклик
```

### Приклад 3: Підстановка конфігурації через MCP

Агент використовує зовнішній MCP-інструмент, передаючи посилання на конфігурацію з чату в аргументах:

```
"{{ref:source=chat,ref=-1,start=export const config}} --host production"
  → конфігурацію з чату підставлено в запит MCP
```
